# Movie Booking — Simple Walkthrough

This file explains the whole codebase in plain language, in the order you
should read it. No prior context assumed.

---

## 1. The story in one paragraph

A theater chain wants an online booking system. An admin first sets up the
"inventory": theaters, movies, and shows (a specific movie playing on a
specific screen at a specific time). A customer then searches for a movie by
title and city, looks at which seats are still free for a chosen show, and
books a handful of them — the system prices each seat by its type (a back-row
recliner costs more than a front-row regular seat), locks those seats down so
nobody else can take them, and creates a confirmed booking. If the customer
changes their mind, they can cancel — the seats go back on sale and the
booking is marked cancelled. Every time a booking is confirmed or cancelled,
the system also fires off notifications (an email and an SMS in this build),
without the booking logic needing to know anything about how those
notifications are delivered.

---

## 2. The one door you're allowed to knock on

`src/services/MovieBookingService.java` is the **only** class anything
outside the package is meant to call. Everything else (`model`, `strategy`,
`factory`, `observer`, `repository`, `exceptions`) is a helper this class
uses internally — think of `MovieBookingService` as the library's public API
and everything else as private implementation.

| Method | What it does |
|---|---|
| `registerObserver(observer)` | Add a listener that gets told about every booking confirm/cancel |
| `addTheater(id, name, city)` | Register a theater |
| `addMovie(id, title, durationMinutes)` | Register a movie |
| `addShow(showId, movieId, theaterId, screenId, screenName, rows, seatsPerRow, startTime, baseSeatPrice)` | Create a show — this is also where the screen's seat grid gets generated |
| `searchShows(movieTitle, city)` | Find shows for a movie in a city |
| `getAvailableSeats(showId)` | List the seats still free for a show |
| `bookSeats(showId, userId, userName, userEmail, seatIds)` | Book a list of seats, get back a `Booking` |
| `cancelBooking(bookingId)` | Cancel a confirmed booking, freeing its seats |

## 3. Read the code in this order

### Step 1 — the building blocks (`src/model/`)

Start here. These are mostly plain data holders — the interesting logic is
concentrated in one of them (`Screen`), which is worth slowing down for.

- **`Movie.java`** — id, title, duration. Nothing else.
- **`Theater.java`** — id, name, city. The `city` field is what
  `searchShows` filters on.
- **`SeatType.java`** — an enum: `REGULAR`, `PREMIUM`, `RECLINER`.
- **`SeatStatus.java`** — an enum: `AVAILABLE`, `BOOKED`. A seat is always in
  exactly one of these two states.
- **`Seat.java`** — a seat id (like `"C2"`), its row/number, its
  `SeatType` (fixed forever once created), and its `SeatStatus` (the one
  mutable field — it flips between `AVAILABLE` and `BOOKED` as bookings and
  cancellations happen).
- **`Screen.java`** — the one model class that actually *does* something.
  Its constructor, `Screen(screenId, name, rows, seatsPerRow)`, doesn't just
  store numbers — it immediately builds every `Seat` object for the whole
  grid via a private helper, `generateSeats(rows, seatsPerRow)`. For each row
  index it calls `seatTypeForRow(rowIndex, totalRows)` to decide whether that
  row is `REGULAR`, `PREMIUM`, or `RECLINER`, using this rule:
  ```java
  if (rowIndex < totalRows * 0.4) {
      return SeatType.REGULAR;
  } else if (rowIndex < totalRows * 0.7) {
      return SeatType.PREMIUM;
  }
  return SeatType.RECLINER;
  ```
  In plain words: the front 40% of rows (closest to the screen) are cheap
  `REGULAR` seats, the next 30% are `PREMIUM`, and the back 30% are
  `RECLINER` — a fairly realistic real-world cinema layout. Because this is
  computed as a *percentage* of `totalRows` rather than a fixed row count, it
  automatically scales to any screen size you ask for (a 5-row screen and a
  20-row screen both get sensible splits). Seat ids are built as
  `rowLabel + number` (e.g. `"C2"` = row C, seat 2), and every seat starts
  life as `AVAILABLE` (see `Seat`'s constructor).
- **`Show.java`** — glues a `Movie` + `Theater` + `Screen` + start time +
  `baseSeatPrice` together. The screen's seats and their fixed types were
  already generated by the time a `Show` is built.
- **`User.java`** — id, name, email. Nothing clever.
- **`BookingStatus.java`** — an enum: `CONFIRMED`, `CANCELLED`.
- **`Booking.java`** — the record of one booking transaction: which show,
  which user, which list of `Seat`s, the `totalAmount` charged, when it was
  made, and its `BookingStatus` (starts `CONFIRMED`, the one mutable field).

**Nothing above (aside from `Screen`'s one-time seat-grid generation)
decides anything on its own — it's mostly storage that `MovieBookingService`
reads and mutates.**

### Step 2 — how a seat's price is calculated (`src/strategy/`)

- **`SeatPricingStrategy.java`** — an interface with one method,
  `calculatePrice(baseSeatPrice)`.
- **`RegularPricingStrategy.java`** — returns `baseSeatPrice` unchanged
  (1.0x).
- **`PremiumPricingStrategy.java`** — returns `baseSeatPrice * 1.5`.
- **`ReclinerPricingStrategy.java`** — returns `baseSeatPrice * 2.0`.

This is the **Strategy pattern**: "how much extra does this seat type cost"
is pulled out into its own small, swappable object instead of being an
`if (seatType == PREMIUM) ... else if ...` chain buried inside the booking
logic. Each show has a single `baseSeatPrice`, and every seat type just
multiplies that base by its own factor.

### Step 3 — how the right strategy gets picked (`src/factory/SeatPricingStrategyFactory.java`)

One static method, `getStrategy(SeatType)`, backed by three pre-built,
shared instances (`REGULAR`, `PREMIUM`, `RECLINER` — created once as
`static final` fields, not re-created per call) and a `switch` expression
that maps each `SeatType` to its matching strategy object. This is the
**Factory pattern**: it exists so that `MovieBookingService` never has to
know or care which concrete `SeatPricingStrategy` class exists — it just
asks the factory "give me the strategy for this seat's type" and gets back
the right object. If a fourth seat type were added later, only this factory
and one new strategy class would need to change — `MovieBookingService`
itself wouldn't need a single new line.

### Step 4 — who gets told about bookings (`src/observer/`)

- **`BookingObserver.java`** — an interface with two methods:
  `onBookingConfirmed(booking)` and `onBookingCancelled(booking)`.
- **`EmailNotificationObserver.java`** — prints an "EMAIL to ..." line to
  the console for both events.
- **`SmsNotificationObserver.java`** — prints an "SMS to ..." line to the
  console for both events.

This is the **Observer pattern**: `MovieBookingService` keeps a plain list
of `BookingObserver`s (registered via `registerObserver`) and, whenever a
booking is confirmed or cancelled, loops over that list and calls the
matching method on each one — without knowing or caring what any given
observer actually does with the notification. `Main.java` registers *both*
`EmailNotificationObserver` and `SmsNotificationObserver` at startup, and
neither observer knows the other exists. If you wanted to add, say, a push
notification, you'd write one new class implementing `BookingObserver` and
register it — nothing in `MovieBookingService` would need to change.

### Step 5 — where things are looked up (`src/repository/`)

- **`ShowRepository.java`** — wraps a `Map<String, Show>`. `save(show)`
  stores it, `findById(showId)` looks it up, and
  `findByMovieTitleAndCity(movieTitle, city)` linearly scans every stored
  show and keeps the ones whose movie title and theater city both match
  (case-insensitively). This is a simple in-memory stand-in for what would
  be a database query in a real system.
- **`BookingRepository.java`** — same idea, but for `Booking`s: `save` and
  `findById`.

Both repositories are intentionally "dumb" — they store and retrieve, they
never validate or decide anything. That's `MovieBookingService`'s job.

### Step 6 — errors (`src/exceptions/`)

Three plain-English failure cases, each its own exception class (all extend
`RuntimeException`, so callers aren't forced to declare/catch them):
- `ShowNotFoundException` — the `showId` given doesn't exist.
- `SeatNotAvailableException` — the seat either doesn't exist on that show's
  screen, or exists but is already `BOOKED`.
- `BookingNotFoundException` — the `bookingId` given doesn't exist, or
  exists but is already `CANCELLED` (cancelling twice is treated the same as
  cancelling something that was never there).

### Step 7 — the orchestrator (`src/services/MovieBookingService.java`)

Now that you've seen every piece, this file just wires them together. The
two methods worth reading closely are `bookSeats` and `cancelBooking` — see
the flow diagrams in section 4 below for the exact order of operations.

Two smaller design details worth noticing while you read it:
- `usersById.computeIfAbsent(userId, id -> new User(id, userName, userEmail))`
  in `bookSeats` — this means a `User` object is created the *first* time a
  given `userId` books anything, and reused (by that same id) on every
  booking after that, without a separate "register a user" step anywhere in
  the public API.
- `bookingSequence`, an `AtomicInteger` starting at 1, generates booking ids
  like `"BK1"`, `"BK2"`, ... via `bookingSequence.getAndIncrement()`. It's
  `Atomic` mainly as a defensive habit (safe under concurrent access) even
  though this particular test harness only ever calls the service from one
  thread.

### Step 8 — the runner (`src/Main.java`)

Not part of the "real" system — a test harness. It reads a text script line
by line (`test/input/scenario.txt`), turns each line into a call on
`MovieBookingService`, and writes what happened to
`test/output/output.txt`. It also anchors a fake "now" (`ANCHOR =
LocalDateTime.of(2026, 8, 8, 9, 0)`) so that show start times computed as
"anchor + N minutes" are reproducible on every run instead of depending on
the real wall-clock time.

## 4. Picture of one full flow: booking, then cancelling

### `bookSeats(showId, userId, userName, userEmail, seatIds)`

```
Main.java (reads "BOOK SH1 U1 Alice alice@test.com A1,C2,E1")
   |
   v
MovieBookingService.bookSeats("SH1", "U1", "Alice", "alice@test.com", [A1, C2, E1])
   |
   | findShow("SH1")                     -> looks up SH1 in ShowRepository, throws
   |                                        ShowNotFoundException if missing
   | usersById.computeIfAbsent("U1", ...) -> creates (or reuses) the User "Alice"
   |
   | for each requested seatId:
   |     show.getScreen().getSeat(seatId)
   |     if seat == null                 -> throw SeatNotAvailableException ("does not exist")
   |     if seat.getStatus() != AVAILABLE -> throw SeatNotAvailableException ("already booked")
   |     (collects all three seats into seatsToBook before touching anything)
   |
   | for each collected seat:
   |     SeatPricingStrategyFactory.getStrategy(seat.getSeatType())
   |     pricingStrategy.calculatePrice(show.getBaseSeatPrice())
   |     totalAmount += that price
   |
   | for each collected seat:
   |     seat.setStatus(BOOKED)          -> only now do seats actually get locked
   |
   | bookingId = "BK" + bookingSequence.getAndIncrement()
   | new Booking(bookingId, show, user, seatsToBook, totalAmount, now)  -> status starts CONFIRMED
   | bookingRepository.save(booking)
   |
   | for each registered BookingObserver:
   |     observer.onBookingConfirmed(booking)
   |        -> EmailNotificationObserver prints "EMAIL to ..."
   |        -> SmsNotificationObserver prints "SMS to ..."
   v
returns the Booking to Main.java, which prints:
"OK booked [A1, C2, E1] -> booking BK1 total $1125.0"
```

Notice the order: **every seat is validated first, and prices are
calculated, before any seat's status is actually flipped to `BOOKED`.** If
seat 2 of 3 turned out to be unavailable, the loop throws before touching
seat 1 or seat 3 at all — so a failed booking never leaves seats
half-locked.

### `cancelBooking(bookingId)`

```
Main.java (reads "CANCEL BK1")
   |
   v
MovieBookingService.cancelBooking("BK1")
   |
   | bookingRepository.findById("BK1")
   | if booking == null OR booking.getStatus() != CONFIRMED
   |     -> throw BookingNotFoundException
   |        (this is why cancelling an already-cancelled booking fails too)
   |
   | for each seat in booking.getSeats():
   |     seat.setStatus(AVAILABLE)        -> seats go back on sale
   |
   | booking.setStatus(CANCELLED)
   |
   | for each registered BookingObserver:
   |     observer.onBookingCancelled(booking)
   |        -> EmailNotificationObserver prints "EMAIL to ... refund $..."
   |        -> SmsNotificationObserver prints "SMS to ... has been cancelled."
   v
Main.java prints: "OK cancelled booking BK1"
```

## 5. Reading the actual captured run (`test/output/output.txt`)

The scenario sets up two theaters, two movies, and two shows, each on a
5-row, 4-seats-per-row screen (20 seats total). Let's follow the real
numbers.

```
> SEATS SH1
SEATS 20 available: A1(REGULAR) A2(REGULAR) A3(REGULAR) A4(REGULAR) B1(REGULAR) B2(REGULAR) B3(REGULAR) B4(REGULAR) C1(PREMIUM) C2(PREMIUM) C3(PREMIUM) C4(PREMIUM) D1(PREMIUM) D2(PREMIUM) D3(PREMIUM) D4(PREMIUM) E1(RECLINER) E2(RECLINER) E3(RECLINER) E4(RECLINER)
```

This is `Screen.seatTypeForRow` in action for `totalRows = 5`: rows A and B
(row indices 0 and 1, both `< 5*0.4 = 2.0`) are `REGULAR`; rows C **and D**
(indices 2 and 3, both `< 5*0.7 = 3.5`) are `PREMIUM`; row E (index 4) is
`RECLINER`. Worth flagging: the comment in `test/input/scenario.txt` above
this line claims "row C PREMIUM; rows D,E RECLINER" — but the real output
(and the real formula) puts **row D in PREMIUM, not RECLINER**. The comment
in the test script is simply wrong; the code's actual, consistent behavior
is what the output above shows.

```
> BOOK SH1 U1 Alice alice@test.com A1,C2,E1
OK booked [A1, C2, E1] -> booking BK1 total $1125.0
```

`SH1`'s `baseSeatPrice` is `250` (from `SHOW SH1 M1 T1 S1 Screen1 5 4 180
250`). A1 is `REGULAR` (250 * 1.0 = 250), C2 is `PREMIUM` (250 * 1.5 =
375), E1 is `RECLINER` (250 * 2.0 = 500). Sum: 250 + 375 + 500 = **1125**,
matching `total $1125.0` exactly.

```
> SEATS SH1
SEATS 17 available: A2(REGULAR) A3(REGULAR) A4(REGULAR) B1(REGULAR) B2(REGULAR) B3(REGULAR) B4(REGULAR) C1(PREMIUM) C3(PREMIUM) C4(PREMIUM) D1(PREMIUM) D2(PREMIUM) D3(PREMIUM) D4(PREMIUM) E2(RECLINER) E3(RECLINER) E4(RECLINER)
```

20 seats minus the 3 just booked (A1, C2, E1 are all gone from this list) =
17 — proving `seat.setStatus(BOOKED)` actually took effect.

```
> BOOK SH1 U2 Bob bob@test.com A1
ERROR SeatNotAvailableException: Seat A1 is already booked for show SH1
> BOOK SH1 U2 Bob bob@test.com Z9
ERROR SeatNotAvailableException: Seat Z9 does not exist on show SH1
```

Two different code paths through the *same* exception class: the first hits
`seat.getStatus() != AVAILABLE`, the second hits `seat == null` (there's no
row "Z" on a 5-row screen).

```
> CANCEL BK1
OK cancelled booking BK1
> SEATS SH1
SEATS 20 available: A1(REGULAR) A2(REGULAR) A3(REGULAR) A4(REGULAR) B1(REGULAR) B2(REGULAR) B3(REGULAR) B4(REGULAR) C1(PREMIUM) C2(PREMIUM) C3(PREMIUM) C4(PREMIUM) D1(PREMIUM) D2(PREMIUM) D3(PREMIUM) D4(PREMIUM) E1(RECLINER) E2(RECLINER) E3(RECLINER) E4(RECLINER)
```

Back to all 20 available — `cancelBooking` walked `booking.getSeats()` and
set every one of them back to `AVAILABLE`.

```
> CANCEL BK1
ERROR BookingNotFoundException: No confirmed booking found with id BK1
```

Same booking id, but now it fails — `booking.getStatus() != CONFIRMED` is
true (it's `CANCELLED`), so `cancelBooking`'s guard treats "already
cancelled" exactly like "never existed."

```
> BOOK SH1 U4 Dan dan@test.com A1
OK booked [A1] -> booking BK3 total $250.0
```

Proof the cancellation genuinely freed A1 again: a brand-new booking (`BK3`
— note `BK2` was used up by the `SH2` booking in between) can take the same
seat. $250 = the `REGULAR` base price with no multiplier, matching A1's
seat type.

## 6. Things to try / test yourself

You can edit `test/input/scenario.txt` and re-run with:
```
javac -d out $(find src -name "*.java")
java -cp out Main test/input/scenario.txt test/output/output.txt
```

1. **Book every seat on a show, then try one more.**
   Add `BOOK` lines until all 20 seats on `SH1` are taken, then one more
   `BOOK SH1 ... <any seat>`. Expect `ERROR SeatNotAvailableException`
   because every seat you try will already be `BOOKED`.

2. **Confirm partial failure doesn't half-book.**
   Try `BOOK SH1 U9 Eve eve@test.com A2,A1` right after A1 is already
   booked (A2 still free). Since A1 fails validation, check with `SEATS
   SH1` afterward that A2 is *still* available too — proving the
   validate-everything-before-booking-anything loop in `bookSeats` works.

3. **Search with a mismatched case.**
   Try `SEARCH inception mumbai` (lowercase) — `ShowRepository`'s
   `equalsIgnoreCase` checks mean this should still find `SH1`.

4. **Build a bigger screen and check the row split.**
   Add a `SHOW` with, say, 10 rows. With `totalRows = 10`: rows with index
   `< 4` (rows A–D) should be `REGULAR`, index `< 7` (rows E–G) `PREMIUM`,
   and the rest (rows H–J) `RECLINER`. Run `SEATS` on it and check the
   printed seat types match that math.

5. **Cancel a booking, then try to cancel it as if it were a fresh unknown id.**
   Compare the error text for cancelling an already-cancelled booking
   (`BK1` above) versus a truly nonexistent one (`BK999`) — both produce
   the same `BookingNotFoundException` message shape, since the code
   treats them identically.

6. **Register a third observer.**
   Add a class implementing `BookingObserver` (e.g. one that just counts
   how many bookings/cancellations it has seen) and register it in
   `Main.java` alongside the email/SMS observers. Confirm all three fire
   on every `BOOK`/`CANCEL` without touching `MovieBookingService` at all —
   this is the payoff of the Observer pattern.

7. **Break something on purpose.**
   Try `BOOK SH1 U1 Alice alice@test.com` with no seat list, or `SHOW
   SH3 M1 T1 S1 Screen1 abc 4 180 250` (a non-number for rows) — see what
   exception you get from `Main.execute`'s parsing and trace it back to
   which `Integer.parseInt`/array-index line threw it.
